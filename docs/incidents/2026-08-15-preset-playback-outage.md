# Incident: TuneIn preset wipe + silent LOCAL_INTERNET_RADIO playback failure

**Date:** 2026-08-15
**Status:** Resolved
**Impact:** All 8 SoundTouch speakers — presets wiped three separate times over one evening, then presets "restored" but silently non-playable for several hours. A later "save to all speakers" test also silently reached only 6 of 8 speakers (see bug #5).

## TL;DR (read this first if you're future-us trying to recall this fast)

Five separate bugs stacked on top of each other in one evening:

1. A buggy HA lovelace "TuneIn Preset Editor" card broadcast unconfirmed preset writes to all speakers, wiping presets household-wide. **Not caused by us tonight — pre-existing card bug.**
2. The safety-net `restore` / `restore-all` endpoints we wrote to fix #1 fired `storePreset` writes to each speaker with **zero delay between them**. Older SoundTouch firmware chokes on that: it wiped 5 more speakers and hard-hung 2 others, which needed a physical power cycle. **Fixed** by adding `asyncio.sleep` pacing (0.6s/write, 1.0s/speaker) inside `api_restore_preset_backup` / `api_restore_all_from_baseline` in `main.py`.
3. After pacing was fixed and presets were restored again, **every preset "worked" (HTTP 200, structurally correct) but nothing audible ever played, on any speaker.** Root cause: missing orion-URL wrapping (`_wrap_local_internet_radio_content_item` fix in `main.py`) — full detail below.
4. Later the same evening, saving a single new preset (via the TuneIn Preset Editor card's "search and save to all speakers" flow) **wiped TheDeck's presets to zero and Seven's down to one**, even though pacing had already been added to the restore endpoints. Root cause: `api_store_preset` — the single-preset endpoint used directly by the webui, HA's `store_preset_radio`/`store_preset_tunein` services, *and* the lovelace card — had no pacing of its own. The card's own "save to all 8 speakers" loop fired 8 back-to-back writes (one per speaker, ~130-300ms apart) with nothing throttling it. **Fixed** by adding a global pacing choke point (`_pace_store_preset_globally()`) directly inside `api_store_preset`, so every caller is protected automatically regardless of how it paces (or doesn't pace) itself.
5. After all of the above was fixed, a live test of the card (swapping preset 6 to "Radio LaB" via the TuneIn Preset Editor's "All" chip) **only reached 6 of 8 speakers** — Pooptown and Downstairs kept their old preset (BE BOP) while the other 6 correctly updated. Not data corruption (unlike #2/#4) — just a silent partial broadcast. Root cause: `_savePreset`/`_saveRadioPreset`/`_savePandoraPreset` in `soundcork-preset-editor.js` ran their per-speaker `store-preset` fetches in a plain sequential loop with **no timeout and no per-speaker failure reporting** — a slow/flaky speaker (matches the known Pooptown/Jefe Negro wifi reliability issue, see "Still open" below) could fail or hang silently and the only visible symptom was, at best, a generic count like "Saved to 6/8 speakers" with no way to tell *which* 2 were skipped. **Fixed** — see full detail below.

### Root cause of #3 (missing orion-wrap on restore)

`Presets.xml` (soundcork's baseline/backup record) stores `LOCAL_INTERNET_RADIO` presets with the **bare external stream URL** in `location`, e.g.:

```xml
<ContentItem source="LOCAL_INTERNET_RADIO" type="stationurl" location="https://wmse.streamguys1.com/wmseliveaac" .../>
```

But the speaker firmware does **not** reliably stream from a bare external URL like that. The webui's own "Save Preset" flow (`soundcork/webui/static/app.js`, ~line 1480-1488) never writes a bare URL — it always wraps it through soundcork's own local proxy first:

```js
const dataPayload = btoa(JSON.stringify({ name, imageUrl: containerArt, streamUrl }));
const location = `${baseUrl}/core02/svc-bmx-adapter-orion/prod/orion/station?data=${dataPayload}`;
```

i.e. the real `location` a working preset needs looks like:

```
http://192.168.1.229:8000/core02/svc-bmx-adapter-orion/prod/orion/station?data=<base64 JSON of {name, imageUrl, streamUrl}>
```

`api_restore_preset_backup` and `api_restore_all_from_baseline` read the bare URL straight out of `Presets.xml`/backups and posted it directly to `/storePreset`, skipping this wrapping step entirely. The write succeeds, `/presets` looks correct, but the speaker firmware never treats it as a real ongoing stream: `nowPlaying` never populates `playStatus`, `track`, or `streamType` for it, and no audio plays. This looked exactly like "everything is broken" even though hardware, network, WiFi, and the household's own `LOCAL_INTERNET_RADIO` architecture were all fine the whole time — Bose's TuneIn API was never involved and never reintroduced.

**Fix:** added `_wrap_local_internet_radio_content_item()` to `main.py`, applying the same wrap the webui does, called from both restore endpoints before every `storePreset` write.

**The same exact bug also existed independently in the HA integration**: `async_store_preset_radio` in `custom_components/soundcork/media_player.py` (the handler behind the `soundcork.store_preset_radio` service — the "Direct Stream" path the card's own warning banner tells you to use instead of TuneIn) wrote the bare `stream_url` straight into `location` too. Fixed the same way: it now base64-encodes `{name, imageUrl, streamUrl}` and points `location` at the orion proxy before building the preset XML, mirroring the webui exactly. Deployed via the FTP add-on, `ha_restart` required to load it.

### Root cause of #4 (unpaced single-preset writes corrupting whole preset stores)

Discovered while trying to save WPR Music to preset 3 via the TuneIn Preset Editor card. The card's "search and save to all speakers" flow calls `POST /api/v1/speakers/{ip}/store-preset` once per selected speaker, back-to-back, with **no delay between calls** — same pattern as bug #2, but this time going through `api_store_preset` (the plain single-preset endpoint), which had never been given any pacing since it isn't part of the restore machinery.

Confirmed via `docker logs soundcork`: 8 `POST .../storePreset` calls at 15:47:08–15:47:09, ~130-300ms apart, from the household's own browser IP. Ground-truth check via `GET http://<ip>:8090/presets` immediately after showed **TheDeck's presets reduced to none at all**, and **Seven's reduced to a single preset** — the other 6 speakers, hit with the same pattern, happened to survive intact this time (data-only difference, not a code difference: see the still-open item on speaker fragility below).

**This means a single unpaced write to a speaker can be enough to corrupt its entire onboard preset store**, not just a repeated burst to the same speaker. Any code path that calls `storePreset` more than once in quick succession — regardless of whether it's hitting the same speaker repeatedly or different speakers once each — needs pacing.

**Fix:** added a process-wide serialized pacing lock directly inside `api_store_preset` itself (`_pace_store_preset_globally()`, `_STORE_PRESET_MIN_INTERVAL_SECONDS = 1.0`), so **every** caller — webui, HA's `store_preset_radio`/`store_preset_tunein` services, the lovelace card, and any future script — is automatically protected, without depending on that caller to pace itself correctly. This is the actual "more hardened interface" fix: the safety now lives at the one place all writes funnel through, not in any particular client.

**Recovery:** ran `POST /api/v1/presets/restore-all` again (now both paced and orion-wrap-safe) to restore TheDeck and Seven to their full 6-preset baseline, verified all 8 speakers intact, then re-applied the correct WPR Music preset to slot 3 on all 8 — this time via a plain script hitting the now-globally-paced `api_store_preset`, verified afterward with zero corruption and confirmed real playback (`playStatus=PLAY_STATE`/`BUFFERING_STATE`, `track=WPR Music`) on TheDeck and Seven specifically (the two that had just proven fragile).

### Bonus finding: preset 4 had been mislabeled "WPR Music" all along

Not something we caused — a pre-existing data issue in the account's baseline, surfaced by this investigation. Preset 4's `location` (`https://wpr-ice.streamguys1.com/wpr-ideas-mp3-64`) is Wisconsin Public Radio's **Ideas Network** (news/talk), not their Music Network — confirmed via `radio-browser.info` and the stream's own `icy-name`/`icy-description` headers (`"Wisconsin Public Radio: The Ideas Network"`). The correct WPR Music Network stream is `https://wpr-ice.streamguys1.com/wpr-music-mp3-96` (`icy-name: WPR Music Network`, genre Classical) — that's what preset 3 now correctly points to.

**Resolved:** household chose to relabel rather than repoint. Preset 3 renamed to **"WPR News/Jazz"** (still streaming `wpr-music-mp3-96`, reusing the `s28585` WPR logo art). Preset 4 renamed to **"WPR Ideas/News"** (stream unchanged, `wpr-ideas-mp3-64`, same `s28585` art). Both applied to all 8 speakers via `api_store_preset` (now globally paced — no corruption on either pass), and both verified with real playback (`playStatus=PLAY_STATE`, correct `track` name) after each change. Final preset lineup on every speaker: `WUWM | WMSE | WPR News/Jazz | WPR Ideas/News | WSUM | BE BOP`.

### Root cause of #5 (silent 6-of-8 partial broadcast in the lovelace card)

After the Radio LaB test only reached 6 of 8 speakers, we first checked whether the card's `speakers:` config for the "TuneIn Preset Editor" (`mode: editor`) card on the `sound-controls` dashboard was simply missing Pooptown/Downstairs. It wasn't — `ha_config_get_dashboard` confirmed all 8 speaker entities (`media_player.the_deck_2`, `media_player.seven_2`, `media_player.thebedroom_2`, `media_player.amelia_s_lair_2`, `media_player.kitchen_2`, `media_player.jefe_negro_2`, `media_player.pooptown`, `media_player.downstairs`) are correctly listed in every card instance's `speakers:` array. (Note: Pooptown/Downstairs use their *un-suffixed* entity_id as the correct soundcork entity — the `soundtouchplus` HACS integration's duplicate registered `_2` for those two instead, the opposite of the other 6 speakers, where soundcork got the `_2` suffix. Both entity IDs were double-checked against `ip_address`/`preset_N_name` attributes to confirm which was actually the soundcork one.)

We then pulled 24h of HA history for all 8 entities' `unavailable` transitions to check whether Pooptown/Downstairs specifically were dropping offline at save time. They weren't singled out — all 8 speakers flipped to `unavailable` and back at the exact same 3 timestamps (09:09:18, 09:18:57, 11:06:53), consistent with HA/integration reloads, not a per-speaker issue. So the config was fine and entity availability wasn't selectively excluding those two.

The actual bug was in the save code itself, in `soundcork-preset-editor.js`. `_savePreset`, `_saveRadioPreset`, and `_savePandoraPreset` each ran their per-speaker `POST .../store-preset` calls in a plain `for` loop with `fetch(...)`/`catch(_){}` and **no `AbortSignal.timeout()`** (unlike `_reachable()` elsewhere in the same file, which does use one) — so a single slow or flaky speaker's request could hang or fail silently, and the loop's only output was a bare `ok`/`ips.length` counter. Depending on exactly where a speaker dropped out (pre-filtered as `unavailable` by `_getSpeakerIps()` before the loop even started, vs. failing mid-loop), the user could see either a plain "Preset saved" success message with no count at all, or a vague "Saved to 6/8 speakers" — neither ever named which speakers were actually skipped. That's how Pooptown and Downstairs silently kept BE BOP while everything else looked like a clean success.

**Fix (deployed to the `sound-controls` dashboard's inline `soundcork-preset-editor` resource via `ha_config_set_dashboard_resource`, and synced into `lovelace-card/soundcork-preset-editor.js` in this repo):**

- Added a shared `_storePresetOnSpeakers(ips, xml)` helper used by all three save flows: each speaker write now has an 8s `AbortSignal.timeout()` and one retry, and the helper returns `{succeeded, failed}` IP lists instead of a bare count.
- Success/partial-failure messages now name the actual speakers, e.g. `Saved to 6/8 speakers - FAILED: Pooptown, Downstairs`, instead of a number with no names attached. The failure message now stays up 8s (was 4s) to give time to read the names.
- `_confirmWrite()` now also checks for and names any speaker that would be silently excluded *before* the write even starts (e.g. genuinely `unavailable` in HA at that moment), appending a `WARNING: skipping <names> (unavailable right now)` line to the confirm dialog — closing the other half of the silent-exclusion gap, since a pre-filtered speaker previously never appeared anywhere in the UI at all.
- Removed a harmless-but-risky duplicate: `_getTargetIps()`/`_getSpeakerNames()` were each defined twice in the file (functionally identical, but a future edit to only one copy could have silently diverged since JS lets the second definition win). Consolidated to one copy each.
- Undo (`_offerUndo`) now only targets the speakers that actually succeeded, not the full requested list.

This doesn't explain *why* Pooptown/Downstairs specifically stalled/failed that one time (no server-side corruption or log anomaly was found — the new pacing lock and orion-wrap fixes were unaffected by this bug), but it ensures the next time any speaker is skipped for any reason, it's named on screen immediately instead of requiring a manual per-speaker check to discover.

**Recovery:** restored BE BOP to preset 6 on all 8 speakers (captured from a live backup of the original `ContentItem` XML before the Radio LaB test), verified via zone-check playback on all 8, including a zone-follower false alarm on Seven (it was following Kitchen from an earlier user test, not actually broken — confirmed via `/getZone` and a direct `PRESET_6` key press).

## Diagnostic playbook (use this next time before going down rabbit holes)

- **`nowPlaying` is not proof of anything for `LOCAL_INTERNET_RADIO`.** On this firmware (`27.0.6.46330.5043500`) it can look completely empty (`<art artImageStatus="SHOW_DEFAULT_IMAGE" />`, no track/playStatus) for a preset that's actually fine, if you hit `/select` with a bare unwrapped URL manually. It only shows real `playStatus=PLAY_STATE` / track data when the `location` is properly orion-wrapped.
- **HTTP 200 from `/storePreset` or `/select` proves nothing about actual audio, or about whether the OTHER presets on that speaker just got wiped.** Both are accept-and-forget from the firmware's perspective. Always follow a write with `GET http://<ip>:8090/presets` to confirm the full preset count is still what you expect.
- **`media_player.py`'s `state` property has a known unrelated bug**: it reports `playing` any time `source != STANDBY`, without checking `play_status`. Don't trust HA's reported "playing" state either — check the speaker's own `/now_playing` `playStatus` field directly.
- **Fastest real verification:** press the actual physical preset key over the speaker's own API (`POST http://<ip>:8090/key` with `PRESET_<n>` press+release) — this is the same path a physical button press takes — then poll `http://<ip>:8090/now_playing` a few seconds later and check for `playStatus>PLAY_STATE` (or `BUFFERING_STATE` if it just started) and a populated `<track>`. If those are present, it's genuinely playing.
- **To sanity-check a stream URL/network path independent of the speaker**: use `curl -A "Bose_Lisa/27.0.6"` etc. from the soundcork box itself, or better, stand up a disposable `python3 -m http.server`-style logger on the soundcork box and point a test preset at it directly — you'll see the real request (including the speaker's actual `User-Agent: Bose_Lisa/27.0.6` and `x-bmx-device-id` header) land in your own log the moment `/select` fires, which conclusively proves the firmware's fetch mechanism itself works.
- **Icecast public listener counts are not reliable evidence** — we tried using WMSE's `/status-json.xsl` listener count as a proxy for "did our speaker connect," but on a real public station with 60+ listeners the count moves on its own; a toggle test came back inconsistent. Don't rely on this again; use the controlled local test-server method above instead.
- **Never fire more than one `storePreset` write without a gap, even to different speakers.** A single unpaced write to a speaker that happens to be busy/flaky can wipe its whole preset store, not just the slot you targeted. This is now handled server-side (see below) but worth remembering if you're ever writing a one-off script that bypasses `api_store_preset`.
- **Before writing any new "save to all speakers" feature**, check `docker logs soundcork --since <window>` around the write burst — the plain access-log lines (`<client_ip> - "POST ... HTTP/1.1" 200`) show you the exact call spacing without needing extra instrumentation.
- **To rename a preset without changing what it plays**, rebuild the same orion-wrapped `location` with the new `name` (keep `streamUrl`/`imageUrl` as-is if unchanged) and push it through `api_store_preset` — see the WPR News/Jazz and WPR Ideas/News renames above for a working example.
- **A "saved to all speakers" UI flow needs three things to be trustworthy, not just one**: (1) an accurate target list (check `ha_config_get_dashboard` for the actual configured `speakers:` array, don't assume), (2) a bounded timeout + retry per speaker so one flaky unit can't hang or silently vanish the whole batch, and (3) failures/exclusions reported **by name**, both before the write (pre-filtered as unavailable) and after (failed in-flight) — a bare `X/Y` count is not enough to know who actually got skipped.
- **Two speakers can share a friendly name across integrations with opposite entity_id suffixing.** Most of this household's speakers have `soundtouchplus` (HACS) registered first (base name) and `soundcork` (custom) registered second (`_2` suffix) — but for Pooptown and Downstairs it's the reverse: `media_player.pooptown`/`media_player.downstairs` (no suffix) are the real soundcork entities, and the `_2` variant (where it exists) is the `soundtouchplus` duplicate. Don't assume the suffix pattern is consistent across all speakers — check `ip_address`/`preset_N_name` attributes to tell them apart.

## Where the code lives / what changed tonight

- `/soundcork/build/main.py` and `/soundcork/repo/soundcork-server/main.py` (kept identical) — patched three times tonight:
  1. Pacing fix: `_PRESET_WRITE_PACING_SECONDS = 0.6`, `_PRESET_SPEAKER_PACING_SECONDS = 1.0`, `asyncio.sleep()` calls added inside `api_restore_preset_backup` and `api_restore_all_from_baseline`.
  2. Orion-wrap fix: `_wrap_local_internet_radio_content_item(preset_elem)` added near the pacing constants; called once per preset, right before `ET.tostring(...)`, in both restore functions.
  3. Global pacing fix: `_pace_store_preset_globally()` (process-wide `asyncio.Lock` + 1.0s minimum interval) added, called at the top of `api_store_preset` before every write — this is the fix that actually closes the door on repeat incidents, since it protects every caller automatically.
  - Backups of every version exist alongside the file as `main.py.bak.<timestamp>` — most recent (post-global-pacing) backup is `main.py.bak.globalpacing.<timestamp>` on both copies, for rollback if ever needed.
  - Note: `/soundcork/build/main.py` also carries a separate, unrelated server-side group-playback orchestration feature (`/api/v1/preset/play`, `/api/v1/select/play`) that predates/is-outside this incident and has not yet been synced into the repo copy — see `docs/deployment.md`.

## Still open / worth revisiting

- **Which speakers are actually fragile is inconsistent.** Pooptown and Jefe Negro didn't reliably retain preset writes across a power cycle earlier tonight. TheDeck and Seven got corrupted by an unpaced *single* write later tonight, while the other 6 (including Pooptown/Jefe Negro) survived the same unpaced burst intact. Later still, Pooptown and Downstairs (not TheDeck/Seven this time) were the two skipped by the silent partial-broadcast bug (#5) — though we found no hard evidence (no `unavailable` flapping, no server log anomaly) that those two are actually less reliable than the rest; it may just be which unit happens to be slow to respond on a given evening. This looks less like "two known-bad units" and more like any of the 8 can be the one that has a rough moment, semi-randomly. The global pacing fix (bug #4) and the new named-failure reporting (bug #5) should make future incidents both less likely and immediately visible regardless of which unit is unlucky, but if a wipe or silent skip ever recurs, suspect aging onboard flash / wifi signal variance across the whole fleet, not just Pooptown/Jefe Negro specifically.
- **`media_player.py` `state` property bug** (reports `playing` without checking `play_status`) — cosmetic, unfixed, low priority.
- **Missing preset artwork**: `LOCAL_INTERNET_RADIO` presets generally show `SHOW_DEFAULT_IMAGE` even when a `containerArt` URL is set and reachable — appears to be a firmware limitation for this source type (art host `cdn-radiotime-logos.tunein.com` is actually still reachable, so it's not a dead-CDN issue), not something worth chasing further right now. (Note: reusing an already-registered TuneIn art URL, like `s28585` above, does display correctly — `IMAGE_PRESENT` confirmed — so the limitation seems specific to non-TuneIn-hosted art URLs, not art in general.)
- **Why Pooptown/Downstairs specifically stalled during the Radio LaB test (bug #5) is still unconfirmed** — the fix makes any future occurrence visible and non-silent, but the underlying trigger (network blip, soundcork-side contention, browser-side timing) wasn't pinned down. Worth a closer look if it recurs now that failures are named — check whether it's always the same 1-2 speakers across multiple future "save to all" attempts, which would point back to a hardware/wifi cause rather than random timing.
- **`/soundcork/build/main.py` vs `/soundcork/repo/soundcork-server/main.py` divergence**: build carries an additional server-side group-playback orchestration feature (`/api/v1/preset/play`, `/api/v1/select/play`) not yet present in the repo copy. Unrelated to this incident's fixes (which are in sync in both), but should be reconciled before the next GitHub push so the repo reflects what's actually running in production.
